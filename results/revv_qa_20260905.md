## 3. Defects

### D-1 — MAJOR — the speed tier can never reach its certified context on a 12GB card

**Repro** (box, no GPU needed):
```
ssh ollama
cd /data/scratch/revv-qa/revv
python3 -c "
import sys; sys.path.insert(0,'.')
import revv
i = revv.read_gguf('/data/models/coding/q36_35ba3b/Qwen3.6-35B-A3B-UD-Q3_K_XL.gguf')
for free in (12043, 12044, 12081, 12082):
    print(free, revv.plan_launch(i, '12gb', None, free).ctx)
"
# 12043 12288 / 12044 12288 / 12081 12288 / 12082 16384
```

**Cause.** `BUILDS["Q3_K_XL_35B"]["peak_mib"] = 11832`, and `model_peak_mib()` anchors that
measurement at `TIERS["12gb"]["ctx"] = 16384` — i.e. the registry asserts 11,832 MiB was
measured *at c=16384*. The context ladder then requires `peak + VRAM_MARGIN_MIB <= free`:

```
11832 + 250 = 12082  >  12044 (hardware maximum)
```

The certified rung is excluded by **38 MiB**. There is no free-VRAM reading on an RTX 3060
12GB at which the planner will select it. The flagship has the identical structure
(11830 + 250 = 12080 > 12044) but its intended ship point *is* 12288, so it lands correctly
by design.

**Why the test suite is green.** `tests/test_planner.py` uses `free_mib = 12287` at
**14 call sites** (lines 67, 84, 101, 121, 127, 132, 148, 208, 235, 252, 267, 283, 295, 365)
— the file itself calls it "the pristine 12,287 fixture". 12,287 MiB free is **physically
unreachable** on this card: 244 MiB is reserved by the driver and appears in neither `used`
nor `free`, capping `memory.free` at 12,044. The decisive assertion is line 365,
*"speed tier: ctx unchanged at 16384"* — it passes only because of an impossible fixture. This is the most important finding in this
report — a green suite is currently masking a real behavioral gap.

**Impact.** Not a crash. c=12288 runs fine and decode rate is only weakly context-dependent,
so 55.9 t/s is probably still approximately reachable. But (a) the shipped config is not the
certified config, (b) `revv inspect` prints "55.9 t/s ... 11,832 MiB peak VRAM" for a config
the tool will not actually launch, and (c) the user silently loses 25% of the advertised
context.

**FIXED** (option 2, per coordinator decision) in dad4f17. Added
`MEASURED_PEAK_MARGIN_MIB = 150`, applied in place of the 250 when the plan's peak is *purely*
a registry measurement.

**Refinement I made and want on the record.** The narrow margin applies only while the peak
stays purely measured. Adding an estimated term on top — the n-gram chain's ~100 MiB, or an
external drafter's weights plus KV — makes the sum part-estimate, and that estimate is exactly
what the 250 exists to cover, so a mixed sum falls back to the wide margin.

This matters because the flagship *does* carry the chain (chain_mib = 100), so it stays on 250
and is **bit-identical to its previous behaviour at every free value**. Without this refinement
the flagship would have taken c=16384 with as little as 150 MiB headroom on a card reporting
free in [12,080, 12,179], undoing the chain-aware step-down certified on 2026-09-05. The speed
tier's 11,832 MiB was measured *with* the chain already running, so its chain_mib is 0 and it
is the one build the narrow margin moves — precisely the intended target.

Verified against the real GGUF headers on the box:

| free | flagship | speed tier |
|---|---|---|
| 12,044 (reference, idle) | c=12288, peak 11,746, headroom 298, `-ctxcp 0` | **c=16384**, peak 11,832, headroom 212, `-ctxcp 0` |
| 11,000 (WSL2-like) | steps down to 4096 | steps down to 4096 |
| forced `--tier` | c=16384 + `-ctxcp 0` + warning | c=16384 + `-ctxcp 0` + warning |

Speed-tier 16384 threshold moved 12,082 → **11,982**, now reachable with 62 MiB to spare.
Flagship unchanged everywhere. `-ctxcp 0` still fires on both tiers.

**Test fixtures replaced.** `REF_3060_FREE_MIB = 12044` and `WSL2_3060_FREE_MIB = 11000`
replace the unreachable 12,287, plus `test_real_hardware_fixtures()` and
`test_forced_tier_guard()`. 65 → 78 assertions, none removed or weakened.

**A second impossible fixture, found while fixing this — now RESOLVED.**
`test_flagship_ngram_chain` asserted the flagship keeps "≥ 400 MiB headroom" at
`free = 12,166`. That free value is also unreachable (ceiling 12,044), and the 400 MiB line was
**never satisfied on a real 3060**.

**Coordinator sign-off (accepted):** the flagship's real headroom is **222 MiB** — measured cert
peak 11,822 MiB at c=12288 against the 12,044 usable ceiling. The certification ran three
consecutive 81%-filled requests clean at that peak with `-ctxcp 0`, and every certified config
on this card lives at ~210–220 MiB real headroom. The "~400 MiB comfort line" was expressed
against the 12,288 **nominal** figure — the same accounting error. The certification standard
is now written down explicitly: **≥200 MiB measured under consecutive deep requests with
`-ctxcp 0`.**

Recorded in BENCHMARKS.md in commit **3ffd89f**: the chain ship-point table now states its
headroom against the usable ceiling (88 / **222** / 378 MiB for c=16384 / 12288 / 8192), and the
ship-point justification reads from the ≥200 MiB standard rather than the artifact comfort line.
The ship point does not move — c=12288 was and remains correct. The file's other two headroom
figures (86 MiB and 214 MiB) already computed against 12,044 and were left alone.

### D-4 — MAJOR — `-t` heuristic does not reproduce the certified 8 on the certifying hardware

`physical_core_count()` returns 8 **on this box only by accident**: the VM exposes 10 vCPUs
with 10 distinct `(physical id, core id)` pairs, and the clamp `min(8, 10)` yields 8.

On the *bare metal* it describes — "3060 + Ryzen 3600 (6 physical / 12 logical)", the exact
machine BENCHMARKS §18's thread sweep was run on — `/proc/cpuinfo` yields **6** unique pairs,
so the function returns **6, not 8**. Per the sweep in BENCHMARKS §18, `-t 6` = 55.1 t/s vs
`-t 8` = 55.9. Small (−1.4%), but it means the heuristic does not reproduce its own certified
operating point, and the docstring at revv.py:193–205 asserts a measurement ("-t 8 is +14.4%
over the server default") that the function will not select on the hardware named in it.

**Relevant to machine #2:** whatever WSL2 reports for `physical id`/`core id` decides this.
Have the founder capture `revv up`'s `-t N` lever line and compare.

**Documented, not changed** (per coordinator: do not overfit to our box). The heuristic keeps
physical-cores-clamped-[4,8]; BENCHMARKS §18 now carries an honest note recording that the
certification ran at `-t 8` on a 10-vCPU guest, that 6-core bare metal yields `-t 6` = 55.1 t/s
(−1.4%) in the same sweep, that `-t 7` = 54.7 and `-t 8` = 55.9, and that users can override.

### D-5 — MAJOR — `--tier` bypasses the checkpoint guard and produces a known-fatal config

**Repro** (box, no GPU needed):
```
REVV_HOME=/data/scratch/revv-qa/home python3 revv.py serve \
  /data/scratch/revv-qa/home/models/Qwen3.8-27B-UD-IQ3_XXS.gguf \
  --tier 12gb --print-command
```
Observed: `... -c 16384 ... --jinja ...` — **`-c 16384` with no `-ctxcp 0`.**

Forcing a tier sets `free_mib = None`, which skips *both* the context ladder *and* the
checkpoint-disable logic (`if peak is not None and free_mib is not None:`, revv.py:2530).
The result is precisely the configuration revv.py:144–151 documents as fatal: "passes its
health check, serves one request, and dies on the next with a cudaGraphInstantiate error."
So `revv up --tier 12gb` on a 12GB card is a loaded gun, and `--tier` is exactly what a user
reaches for when auto-detection annoys them.

**FIXED** in dad4f17. Forced-tier mode now *always* sets `ctx_checkpoints = 0` and emits:

> `WARNING --tier was given, so revv did NOT read free VRAM: the context above is the tier's
> declared 16,384, not a measured fit, and could OOM. Context checkpoints are disabled
> (-ctxcp 0) because headroom is unknown. Drop --tier to let revv size this against the
> actual card.`

Headroom there is not large, it is *unknown*, and ~2.7% on short prompts is the cheap side of
that bet. Verified: STOCK mode still emits no `-ctxcp` (the flag lives inside the `MODE_REVV`
block), so the "STOCK stays stock" assertion is unaffected. Covered by the new
`test_forced_tier_guard()`.

### D-14 — MINOR (new, found via the measured-peak sign-off) — the planner's peak estimate is systematically optimistic off-anchor, and grows more so as it steps DOWN the ladder

`model_peak_mib()` anchors a registry build on its measured `peak_mib` and then moves **only the
KV term** with context. Comparing that model against the three measured points now recorded in
BENCHMARKS.md's chain table:

| context | planner estimate | measured | planner is optimistic by |
|---|---:|---:|---:|
| 16384 (the anchor) | 11,930 | 11,956 | 26 MiB |
| 12288 (the ship point) | 11,746 | 11,822 | **76 MiB** |
| 8192 | 11,562 | 11,666 | **104 MiB** |

The error is smallest at the anchor and grows as the planner steps *down*, which is what you
would expect if the non-KV footprint (compute buffers) does not shrink as fast as the model
assumes — the anchor-scaling attributes all context-dependence to KV.

**Why it matters for machine #2 specifically:** the low-VRAM WSL2 regime is exactly where the
ladder steps down, so it is where the estimate is least accurate. At c=8192 the 104 MiB of
optimism consumes 42% of the flagship's 250 MiB margin, leaving ~146 MiB of true buffer.

**Not a live defect and I did not change it.** Every shipped configuration still clears the
≥200 MiB measured standard (flagship c=12288 at 222 MiB, speed tier c=16384 at 212 MiB), and the
speed tier has no error at all at its ship point because that ship point *is* its anchor. But
the planner's own reported headroom should be read as an upper bound, not a measurement — and if
the ladder's lower rungs ever get certified, this is the term to re-measure first.

### D-16 — MAJOR — `revv bench` grades every build against the 27B dense reference, so it cannot detect a MoE regression

**Observed** on the MoE build, which measured 55.94 t/s:
```

  speculation off (what MTP buys you)            22.5 t/s

55.94 t/s is not "within 5%" of 36.9 — it is 51% above it.

contradicts TEST_3060.md, which (after 507544d) tells the tester to expect ~55.9 there.

### D-17 — MAJOR — `revv toggle` and `revv compare` are broken on the MoE build (a 12GB card cannot run its STOCK arm)

**Repro:** with the MoE build up, `revv toggle` → `error: the switch failed: HTTP Error 500`.
`revv compare` → `error: comparison failed: HTTP Error 500` at "STOCK switching...".

Server log:
```
ggml_backend_cuda_buffer_type_alloc_buffer: allocating 15499.34 MiB on device 0:
    cudaMalloc failed: out of memory
alloc_tensor_range: failed to allocate CUDA0 buffer of size 16252234240
llama_model_load: error loading model: unable to allocate CUDA0 buffer
srv  llama_server: exiting due to model loading error
```

STOCK mode deliberately omits `--n-cpu-moe 16` (there is even a test asserting it:
"STOCK mode does not offload experts"). But on the MoE build that flag is not a revv *lever* —
it is what makes a 16 GiB model fit on a 12 GiB card at all. Without it llama-server tries to
put all 15.5 GiB of weights in VRAM and dies. STOCK also uses f16 KV, compounding it.

So the two most demo-able commands fail on what is now the **default** build. `revv compare` is
described in the README as the demo.

Mitigations observed: the failure is not fatal to the daemon — `compare`'s `finally` block
restored REVV mode and the server recovered (health ok, 11 requests served). But `revv status`
reported `mode STOCK` after the failed toggle even though the backend had died, so the recorded
mode and reality disagreed until the next successful switch.

**FIXED** (9726895), per coordinator decision: **STOCK is now defined per build.**
`-ngl 99` is not a slow baseline for the MoE build, it is an impossible one, so its STOCK arm is
the certified nominal baseline **B2** — `-ngl 30 -c 16384`, no expert offload, no speculation,
default KV and threads, measured 22.17 t/s — which is the comparator behind the published 2.52×.
The dense build keeps the config it had. Carried in `BUILDS[...]["stock"]` and applied by
`build_server_argv`; `compare` now prints which stock definition it used.

Also fixed on this path:
- **Anti-fake A/B:** `compare` refuses outright when the two arms would launch byte-identical
  argv. `tuning_is_noop` reasons about levers; this asks the question that settles it.
- **The state inconsistency:** `Backend.start()` committed `self.mode` *before* launching, so a
  failed switch left the endpoint reporting the mode that had just failed with no process behind
  it. Mode is now committed only after the backend is healthy, and `status` reports
  `backend_alive` first, ahead of any line that would read as healthy.

**Verified live on the reference 3060** — the command that used to return HTTP 500:
```
  stock    llama-server defaults with -ngl 30 so the model fits

### D-18 — MINOR — `revv status` overstated free VRAM by the driver reservation, disabling its own near-ceiling warning — **FIXED** (45cb037)

`cmd_status` computed `head = g.total_mib - g.used_mib`. With the MoE build loaded it printed
`11,660 MiB used of 12,288 MiB (628 MiB free)` while `nvidia-smi` reported **384 MiB** free —
the same nominal-vs-usable error corrected in BENCHMARKS (3ffd89f), this time in the live UI.
`GPU.free_mib` and `GPU.reserved_mib` already existed and were not used.

The consequence is not just cosmetic: the near-ceiling note is gated on `head < 200`. Computed
from the inflated figure it could never fire — real free would have to go negative first. The
warning was dead code on this hardware.

Fixed to read `g.free_mib`, report the host reservation on its own line the way `doctor` already
does, and drop the `used > CERT_PEAK_MIB` half of the condition — which suppressed the note in
exactly the case that warrants it, since the measured dense peak (11,822) is *below*
`CERT_PEAK_MIB` (11,958) while sitting 222 MiB from the usable ceiling.
